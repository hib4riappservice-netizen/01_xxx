# 技術的決定の記録

`rules/60-delivery-ops.md` OPS-04（SHOULD）に基づく。判断とその理由を残す。

> **このリポジトリをテンプレートとして複製した場合の扱い**
>
> 以下の記録は2種類に分かれる。
>
> - **[汎用]** — このテンプレートを使う限り、どのサービスでも同じ判断になる。**残す**
> - **[固有]** — テンプレート元（`01_xxx`）でのみ起きた出来事。**新サービスでは削除してよい**
>
> 新しいサービスを立ち上げたら、[固有] の項目を消してから使い始めること。

## [汎用] 2026-08-17: G0に「プラットフォーム標準機能との重複確認」をMUSTとして追加する

**背景**: このテンプレートから作った最初のサービス（googleAccountServiceList）で、
「Gmailを検索して登録済みサービスを検出・一覧化する」機能を、要件定義・実装・
デザイン改善・検出精度の改善まで一通り完了させた後になって、Gmail自体に
「配信登録を管理」（Manage Subscriptions）という、ほぼ同じ課題
（このメールアドレスで何を受信登録しているか把握する）を解決する標準機能が
既に存在することにCEOが気づいた。調査の結果、両者には実質的な差分
（Gmail標準機能はList-Unsubscribeヘッダ付きの配信メールのみが対象で、
トランザクションメール主体のサービスは拾えない／送信者の厳密一致でしか
重複排除しない等）はあったが、"何時間もかけてOAuth審査の準備まで進めた後に
気づいた"という順序自体が問題だった。

**決定**: `rules/01-definition-of-done.md` G0に、「連携先プラットフォームに同じ課題を
解決する公式・標準機能が無いか確認する」ことをMUSTとして追加した。既存の
「作らない判断（既存ライブラリで足りないか）」はSHOULDのままだが、これは
コード実装の代替手段の話であり、今回のケースは「機能・プロダクトそのもの」の
重複という一段上のレベルの話だったため、別項目として明示した。

**理由**: `00-principles.md`のP6「人の注意力に依存しない」の応用。「既存サービスが
無いか調べる」という判断を実装者の注意力・常識に委ねると、今回のように大きな
手戻りが起きる。G0（着手前）の機械的なチェック項目として明文化し、次に同じ轍を
踏まないようにする。

## [汎用] 2026-08-17: デザインレビューのチェックリストを追加する（複製先サービスでの2回の指摘から）

**背景**: このテンプレートから作った最初のサービス（googleAccountServiceList）で、
デザイン実装後にCEOから「配色がイケてない」「各ページからトップへ戻れない」
「フッターが固定されていない」「アイコンが無く殺風景」「装飾要素（アバター）が無駄」
「ボタンが全部同じ色でUXが悪い」「Google連携ボタンの色がブランドと違う」
「使い方と注意書きが混在」「タグラインの折り返しが気持ち悪い」という、同趣旨の指摘を
2回（2026-08-16, 2026-08-17）連続で受けた。`pnpm verify`が緑でも、これらは一切
検出できない。実装者・レビュワーの双方が見落としやすい観点として、次にテンプレートを
使う誰か（自分自身を含む）が同じ指摘を繰り返し受けないよう、恒久的なチェックリストとして
`rules/checklists/feature.md`「デザイン（見た目）を変更した場合（追加）」と
`rules/checklists/human.md`「デザイン（見た目）を変更した場合」に追加した。

**理由**: `00-principles.md` P6「人の注意力に依存しない。機械が落とせる形に変換する」の
応用。機械化できない項目（配色の役割分担、装飾要素の要否等）は`[人間]`タグのまま
チェックリストに残し、少なくとも「確認すべき項目として存在する」状態にする。
全ルートのトップへの導線確認だけは`[要自動化]`としてE2E化の余地を残した。

## [汎用] 2026-08-15: 最初の複製先サービスで見つかったテンプレートの3つの抜けを直す

**背景**: このテンプレートから作った最初のサービス（googleAccountServiceList）で、
認証機能とテストを実装する過程で、テンプレート自体に埋め込まれたまま気づかれていなかった
不備が3件見つかった。いずれも「その状況（`data/`を作る、コンポーネントテストを複数書く、
ボタンを2つ以上置く）になって初めて顕在化する」性質のため、テンプレートの現在の空の
状態では検出されない。

**決定**:

1. `server-only`を依存に追加した。`rules/10-architecture.md` ARC-03が
   `data/`配下に`import 'server-only'`を要求するが、パッケージ自体が入っていなかった。
   Next.jsのバンドラーは未インストールでも解決するが、Vitestは解決できずテストが壊れる。
2. `tests/setup.ts`に`afterEach(cleanup)`を追加した。`@testing-library/react`の自動cleanupは
   `vitest.config.ts`の`globals: true`に依存するが、このテンプレートは有効化していないため
   自動検出されず、同一ファイル内の複数テストでDOMが蓄積し、2つ目以降のテストで
   「複数要素が見つかった」エラーになる。
3. `app/globals.css`に`button`の最小サイズ（24x24px相当）を追加した。
   `* { padding: 0; margin: 0 }`のリセットにより、素の`<button>`はheight 22px程度まで潰れ、
   `tests/e2e/accessibility.spec.ts`のaxe-coreチェック（target-size, WCAG 2.2）に違反する。
   ボタンを1つも置いていない現在のテンプレートの状態では顕在化しないが、
   実際に最初のサービスで2つ以上のボタンを置いた際に検出された。

**理由**: `00-principles.md` P6「人の注意力に依存しない」。いずれも「気をつければ避けられる」
類の不備ではなく、テンプレートの現状（空のscaffold）では機械的に検出しようがなかった。
次に複製するサービスが同じ壁に当たらないよう、今のうちに直す。

## [汎用] 2026-08-14: 技術判断を人間に振らない運用ルール（P9）を追加する

**背景**: 依頼者（CEO）は設計・実装・セキュリティの専門知識を前提にできない。
「これでいいですか」と技術的な選択肢を尋ねられても判断できず、かつ最終責任は
依頼者が持つという状況で、これまでの運用（`spec-writer` 等が技術的な実装方法まで
質問する）は依頼者に負担を強いていた（`googleAccountServiceList` での機能開発中に発覚）。

**決定**: `00-principles.md` に **P9** を新設した。人間に判断を仰ぐのは
「お金」「個人情報の取扱い方針」「機械判定できない最終確認・最終承認」の3種類だけとし、
それ以外の技術判断（ライブラリ選定、DAL/型設計、検出アルゴリズム等）はエージェントが
`rules/` を基準に自分で決め、`docs/decisions.md` に理由を記録する。人間に見せる前に、
`pnpm verify` とレビュー3体の Critical/High 指摘をすべて解消するまで自律的に繰り返す。
`70-loop-engineering.md`（LOOP-04/05）と `.claude/agents/spec-writer.md`、
`docs/PLAYBOOK.md` を P9 に合わせて更新した。

**理由**: `00-principles.md` P6「人の注意力に依存しない」の応用。専門知識のない依頼者に
技術的な合否判定を委ねること自体が、機能しない基準になる。機械的に決着できる技術判断を
人間の確認待ちにすると、レビューが素通りする（人間が「よく分からないが承認する」以外の
選択肢を持てない）リスクがある。

## [固有] 2026-08-12: ブランチ保護をローカルフックで代替する

> この決定は下記「2026-08-13: GitHub branch ruleset」で置き換え済み。
> 経緯を残すために保持している。新サービスでは不要。

**背景**: DEV-01 (MUST)「`main` に直接コミットしない」をサーバー側（GitHub branch
ruleset）で強制しようとしたが、非公開リポジトリでは GitHub Pro 以上が必要
（Free プランは 403 で拒否される）。

**決定**: `.githooks/pre-commit` でローカルに同等のゲートを実装する。
`git config core.hooksPath .githooks` で有効化し、`main` ブランチでの
コミットを拒否する。緊急時は `ALLOW_COMMIT_ON_MAIN=1` で解除できる。

**理由**: `00-principles.md` P6「人の注意力に依存しない。機械が落とせる形に
変換する」に従う。サーバー側で強制できないなら、次善としてローカルで
機械的に落とす。

**既知の限界**: `core.hooksPath` はクローンごとのローカル設定であり、
リポジトリに含めても自動では有効化されない。新しく clone した環境では
`git config core.hooksPath .githooks` を手動で実行する必要がある
（`README.md` のセットアップ手順に明記すること）。また `git commit --no-verify`
で回避できる — これは Git 標準機能であり、フック自体では防げない。
真の強制が必要になったら、リポジトリを Public にするか GitHub Pro に
アップグレードして ruleset を使う。

## [汎用] 2026-08-12: CSP の `script-src` に `unsafe-inline` を許可する

**背景**: `checklists/release.md` SEC-92「`unsafe-inline` を避けている」を満たすため、
`next.config.ts` で `script-src 'self'` を試した。

**決定**: `script-src 'self' 'unsafe-inline'` を採用する。

**理由**: `next build && next start` の状態で Playwright を使って実測したところ、
`unsafe-inline` を外すと Next.js が RSC のペイロードを渡すために注入するインラインscriptが
CSP違反でブロックされ、ハイドレーションが壊れた（`React error #412`、コンソールにCSP違反2件）。
現時点ではペイロードに機微情報を含む機能（認証・決済等）が無いため、この妥協を許容する。

**見直し条件**: 認証や決済など、XSS経由のインラインscript実行が実害に直結する機能を追加する
タイミングで、`middleware.ts` によるnonceベースのCSPへ移行し、`unsafe-inline` を外す。

## [汎用] 2026-08-13: GitHub branch ruleset で main を保護する（ローカルフックから移行）

> **新サービスでは、この ruleset を手動で作成し直す必要がある。**
> GitHubのテンプレート複製では ruleset が引き継がれない（`docs/PLAYBOOK.md` 参照）。

**背景**: 2026-08-12の決定で「非公開リポジトリではGitHub Pro必須のため、
`.githooks/pre-commit`で代替する」とした。その後リポジトリを公開に変更した。

**決定**: `protect-main` ruleset（`pull_request`必須・`deletion`禁止・`non_fast_forward`禁止）を
作成した。**サーバー側への直接pushを実際に試し、`GH013: Repository rule violations`で
拒否されることを実測確認済み。**

**理由**: 公開リポジトリになった時点で、2026-08-12の決定が記録した「見直し条件」
（Publicにするか GitHub Pro にアップグレードする）が満たされたのに、
しばらく対応されていなかった（別セッションの監査で指摘された）。
ローカルフック（`.githooks/pre-commit`）は`--no-verify`で回避できる弱い防御であり、
サーバー側の強制に置き換えられるなら置き換えるべき。

**`.githooks/pre-commit` は残す。** ruleset は「PRを経由すること」は強制するが、
ローカルの早期フィードバック（コミット前に気づく）の価値は別にあるため。

## [固有] 2026-08-13: PR#2（Next.js基盤整備）が400行ルールに違反していたことを記録する

**発覚経緯**: 監査（loop-auditor-2、指摘A-2）で、`scripts/check-diff-size.mjs`導入
（PR#6）より前にマージされたPR#2の差分を同じ計測方法で測ったところ **405行**
（`git diff --shortstat 92115bd e4c9c4f -- . ':(exclude)pnpm-lock.yaml' ...`）で、
`01-definition-of-done.md` G0「差分400行以内・例外なし」に違反していたことが判明した。

**対応しない。** 理由: PR#2は`check-diff-size.mjs`が存在する前にマージされており、
当時は機械判定できなかった（G1の実体である`pnpm verify`自体がPR#2で初めて作られている）。
今からこのコミットを分割・書き換えるのは、履歴の書き換えという別のコストを払うだけで
実益が無い。**記録として残し、繰り返さないことを優先する。**

**再発防止**: `check-diff-size.mjs`は現在CIに接続済みで、以降のすべてのPRに対して
機械的に強制される（PR#3〜#9で実際に機能したことを確認済み）。
